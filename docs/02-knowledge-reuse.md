# 02｜把反馈变成下次能用的知识

反复解释同一要求，通常意味着要求还留在某段聊天里。可复用的做法，是把已经确认、确有适用范围的经验写入一份现行正文，让后续任务找到它、读到它，再用实际结果验证它。

本篇适合持续项目和重复交付，例如每月报告、固定格式文档、代码维护。一次性问答不必建立知识库。下面的目录、反馈分类和验收步骤是本手册建议的工作方法，不是产品自动提供的记忆机制。

## 先判断反馈属于哪一种

| 状态 | 例子 | 如何处理 |
| --- | --- | --- |
| 已确认的长期偏好 | “以后内部审批邮件都用编号段落。” | 写入对应场景的写作规范，保留适用范围。 |
| 已验收的具体版本 | “这份排版可以，就用这一版。” | 保存模板或样例；先沿用到同类交付，不自行扩大为所有文档的规则。 |
| 已验证的方法 | 某种处理流程在明确条件下解决了问题 | 记录条件、步骤、验证依据和限制；单次成功不能证明适用于所有环境。 |
| 当前项目事实 | 文件已完成到哪一步、哪个问题仍未解决 | 写入项目上下文，注明日期和来源；易变信息下次使用前核验。 |
| 候选、推测或仅本次例外 | “可以试试这种格式”“这次先这样” | 留在待验证事项或当前任务里，尚不提升为长期规范。 |

“以后都这样”与“这次可以”应产生不同的保存结果。用户明确要求只读、不保存时，应保留这一边界。没有新反馈或新验证结果，就不必为收尾增添一份总结。

## 同一个问题，只维护一份现行正文

可以用简短的 `AGENTS.md` 提供工作约定和入口，用 `ROUTING.md` 按交付目的指向专业规范；具体方法放在 `standards/`，确认过的模板放在 `templates/`。项目自己的事实留在项目目录。目录名只是示例，可按现有结构调整。

例如，“报告如何排版”只有一份现行规范。不同项目入口链接到它，不各抄一份全文。修改时更新这份正文并回读差异；旧版本可由版本记录保留，不再作为另一个“最新版”继续维护。如此才能明确哪份规则生效，也方便撤回错误修改。

路由应回答“这次要交付什么”。做报告就读取报告规范的相关段落；维护代码就进入开发规范。只有需要项目原件或历史决策时，才继续查项目索引与少量原始记录。不要为了一个小任务遍历全部聊天、全部技能和全部知识文件。

## 准确理解 AGENTS.md 的加载边界

官方文档说明，Codex 在启动时构建指令链：读取全局约定，再沿项目根到当前工作目录的路径发现项目指令；同目录优先选择 `AGENTS.override.md`，其次是 `AGENTS.md`，再考虑配置中的候选文件名。没有项目根时只检查当前目录。它不会因此自动遍历整个仓库的所有子目录。发现顺序、大小限制及配置细节以当前[官方 AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)为准。

`ROUTING.md`、`context.md` 和被链接的专业正文通常是普通资料文件。除非另有加载配置，不能只凭文件存在或出现一个链接，就认定内容已经进入任务上下文。入口应明确要求助手按任务读取相关文件，并在验收时检查实际读取与应用结果。对进行中的聊天，也不要假定文件修改后旧上下文已自动刷新。

本手册建议在入口保留一句可执行的要求：开始相关任务时，先从用途导航定位现行正文，只读必要段落；无法访问时说明限制。跨目录读取规范，并不改变当前工作目录、操作权限或用户本次授权。

## 用最小上下文衔接持续项目

项目 `context.md` 用于说明“现在做到哪里”，不应成为聊天全文的副本。保留目标与范围、已验证状态、下一步、阻塞项、日期与证据入口即可。把推测放入单独的待确认项，避免下一位助手把它当成事实。

一个虚构的例子：

```text
目标：完成一份内部培训讲义，交付可编辑文件和 PDF。
范围：本轮调整结构与版式，暂不对外发布。
已验证：目录结构已确认；示例页已完成并检查。
待完成：剩余章节排版、导出后逐页检查。
待确认：引用图片的使用范围。
依据：保留原始材料、确认记录及对应日期的链接。
```

长期方法引用专业正文，别再抄入上下文。敏感业务材料只保留必要的本地入口，不为了“记得更全”把客户信息、凭据或整段聊天搬入共享知识库。正式记忆、应用数据库等有各自的维护边界，本流程不提供改写它们的授权。

## 保存之后，用一次真实任务验收

一次维护可以控制在四步内：

1. 确认反馈的状态与范围，找到现行正文；发现冲突时保留双方依据，先判断适用场景。
2. 在已有授权内修改最小内容，保留版本或可恢复副本；不覆盖别人的并发修改。
3. 回读新正文与差异，检查链接、示例、限制和旧规则是否一致。
4. 在合适的新任务中使用它，核对助手是否读到正确材料，交付物是否满足具体要求。

例如，验证“编号段落邮件”规则，应检查一封实际草稿的结构和复制效果；验证文档模板，应打开或渲染成品看排版；验证代码方法，应运行对应行为检查。让模型回答“我已理解”只能作为沟通，不能代替这些验收。官方[最佳实践](https://learn.chatgpt.com/docs/learn/best-practices)也强调明确完成条件、保留可复用指导并验证结果。

若当前请求与旧规范冲突，先遵守本次请求及更高优先级的约束，再判断是否需要更新规范。无法确定新要求是长期变化还是单次例外时，只保留当前任务可确认的部分，不贸然推广。遇到不可访问的来源或未经验证的方法，标明缺口，不编写“已验证”的结论。

收尾只陈述到实际达到的阶段：正文已保存、版本已提交、目标设备已收到，或新任务已经验收。知识文件的作用是改善下次提供给模型的上下文；这不是训练模型，也不保证模型永久记住所有历史。更换环境或开始新任务后，仍需确认来源可读、要求被正确应用。项目与聊天的具体关系可参考[官方项目说明](https://learn.chatgpt.com/docs/projects)。
