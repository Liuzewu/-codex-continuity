# 03｜让多台设备使用同一份知识

跨设备复用应先做到两件事：接收端拿到了正确版本，接收端的新任务确实使用了它。只看到远程电脑在线、仓库提交相同或侧栏名称相同，都不足以证明交付行为一致。

本篇提供一套文档同步与验收方法，适合个人在多台电脑间复用规范和模板。它不迁移应用数据库、聊天归属或设备配对，也不要求先部署后台服务。建议先把人工流程跑通，确有重复负担后再考虑自动化。

## 划定同步范围

为可复用知识建立独立仓库，每台设备保留自己的工作副本。首先使用明确的文档白名单，例如 `ROUTING.md`、`standards/`、`templates/`；审查新增文件后再纳入。白名单能缩小范围，但不能代替内容检查：模板里也可能含有真实姓名、地址或客户数据。

区分三类内容会更容易维护：

| 内容 | 保存方式 |
| --- | --- |
| 通用方法、规范、脱敏模板 | 经审查进入知识仓库，维护唯一现行正文。 |
| 设备路径、运行环境、字体位置等适配信息 | 留在设备本地；共享正文只描述需要什么条件。 |
| 客户资料、当前业务状态、原始交付物 | 留在原业务位置，按实际需要与权限引用。 |

不要把整个 `.codex` 目录作为知识包复制。配置、令牌、配对材料、应用数据库、缓存和聊天状态不属于本流程；把它们混入文件同步，无法保证另一台设备安全、正确地接续工作。仓库设为私有也不等于可以省略敏感信息检查。

## 先人工拉取，再核对差异

第一次只选少量规范和一个不含敏感内容的模板。先在一台设备完成修改和本地验收，再传给另一台，确认接收结果后才扩大范围。

1. 在发送端检查工作区和暂存区，阅读本次差异，确认只包含批准的知识文件；审查后提交并推送到已选定且获准使用的仓库。保留已有修改，不把无关文件顺手提交。
2. 在接收端检查本地修改与当前版本；若有未完成工作，先妥善保存，避免拉取时覆盖或混合。
3. 获取远端更新并审阅差异。确认分支关系允许时，采用仅快进的拉取，例如 `git pull --ff-only`；它拒绝分叉时，停下来处理版本关系。
4. 回读接收端的现行正文、用途导航及模板，随后完成下面的五层验收。

本仓库的 `tools/compare_knowledge.py` 可只读比较两个已有目录。通过 `--include standards --include templates --include ROUTING.md` 选定范围，参数形式以它的 `--help` 为准。它按字节计算 SHA 并报告差异，不联网、不写入、不执行同步。左右目录必须先通过正常流程准备好，不能拿一份本地副本冒充远端实时状态。

哈希一致证明所比较文件的字节一致，不证明目录外也一致、规则已经加载或模型理解正确。哈希不同也未必是内容冲突，可能只是行尾不同；应查看实际差异，而不是为让数值相同而覆盖文件。

## 发生冲突时，先保护双方内容

同一文件在两端都被修改时，先保留两边版本和共同基线，再逐段决定合并结果。时间较新不自动代表正确；一端删除、另一端修改，或文件改名、路径大小写变化，都需要结合意图处理。

不要用强制推送、硬重置或清理未跟踪文件来“解决同步”。本方法也不把自动 rebase 或整库覆盖作为默认步骤。若能确认修改的是互不相关的文件，可在审查后正常合并；存在同一规则的不同解释时，先明确适用范围再形成一个现行版本。无法判断就停止该项同步，其他不依赖它的工作仍可继续。

## 按五层检查是否真正生效

| 层次 | 要核验的事实 | 能证明什么 |
| --- | --- | --- |
| 文件 | 接收端版本、目标文件差异或哈希 | 指定知识已到达。 |
| 入口 | 当前项目入口能找到用途导航和正文 | 新任务有可用的读取路径。 |
| 模型读取 | 本次任务实际读取了正确正文，并据此处理要求 | 知识进入了这次工作流程。 |
| 环境 | 路径、权限、工具、字体和依赖满足要求 | 当前设备具备执行条件。 |
| 真实交付 | 成品按约定检查通过 | 该任务在这台设备上完成了复用验证。 |

可以用一份虚构的培训讲义做首轮验收：两端采用同一模板，各生成一个短文档，打开或渲染后检查字体、换行和导出结果。不要用“助手能复述规则”替代成品检查，也不要从一个样例推断所有历史知识都已迁移。

在 macOS 与 Windows 间尤其需要核验：文件名大小写和 Unicode 表示、Git 行尾处理、盘符与目录分隔符、路径长度与可用名称、符号链接与访问权限。模板还可能依赖字体、插件、外部图片或运行库。相同文档放在不同环境里，渲染结果仍可能不同；可执行文件的版本与安装位置也需要单独检查。

为减少后续歧义，可以在仓库中约定文件命名与文本行尾。不要在已有仓库里未经审查就批量改名、统一编码或转换行尾，以免把真实内容修改埋在大批格式差异里。

## 稳定之后，再决定是否自动化

只有人工流程已能反复完成、冲突处理清楚、运行成本可接受时，才考虑条件式自动化。先定义允许同步的文件、网络与电源条件、编辑静默期、运行次数和失败后的退避方式；失败应保留现场，不能无限重试或擅自扩大权限。自动同步文件也不需要后台模型遍历全部历史。

本仓库只提供只读比较工具，不提供自动部署、后台模型调用或替用户更改计划任务的程序。设置自动化属于单独的实施决定。官方[最佳实践](https://learn.chatgpt.com/docs/learn/best-practices)同样建议先稳定工作流，再安排重复运行。

最后，分别报告“知识同步”和“远程访问”的结果。官方[远程连接说明](https://learn.chatgpt.com/docs/remote-connections)描述的是使用连接主机的项目、文件与工具；因此，连接成功不能当作两台电脑各自知识副本一致的证据。手机能看见某个任务，也不能据此保证手机侧栏、桌面分组或本地聊天数据库已同步。不同项目和聊天形态的关系，应以当前[官方项目说明](https://learn.chatgpt.com/docs/projects)及实际界面为准。

一份简短验收记录只需写明比较范围、接收端观察时间、已通过的层次与未测事项。若只验证了文件，就如实写“文件一致”；只有实际任务通过后，才写“本次交付已在接收端验证”。
