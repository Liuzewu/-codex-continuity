# 把私人经验整理成公开资料

公开分享应从一个新的导出目录开始。原始资料只作为理解方法的依据，逐篇重写通用结论；不要先复制整库，再依赖全局替换删姓名。

## 先决定什么可以公开

| 可以重新提炼 | 留在私人环境 |
| --- | --- |
| 工作步骤、检查方法、停止和回退条件 | 原始聊天、屏幕录制、日志和维护回执 |
| 空白模板、字段定义、虚构样例 | 合同、周报、账单、客户资料及真实业务判断 |
| 通用排版要求、审阅清单 | 签章、证件、个人联系方式、客户或同事身份 |
| 可移植的短提示词和工具接口 | 密码、令牌、恢复密钥、授权与配对数据 |
| 对限制和故障类型的概括 | 用户目录、设备名、地址、网络指纹、聊天和项目 ID |

“没有密码”不等于“可以公开”。项目名称、业务金额、时间线、内部角色或多个普通细节组合起来，也可能识别出一个人或客户。对通用方法没有必要的信息，直接舍去。

## 一次公开导出的顺序

1. **缩小来源。** 只读与目标专题有关的规范和技术记录，不把整个个人目录加入整理范围。
2. **重新写稿。** 用自己的结构解释方法。示例统一使用相对路径、空白字段或明确的虚构数据；不做“真实记录换几个名字”的处理。
3. **确认权利。** 私人使用过的插件、第三方技能、公司模板不自动获得再分发权。优先写原创方法，引用官方文档；需要复制时先检查许可证和署名要求。
4. **隔离文件。** 私有来源映射和审阅记录放在公开目录之外。公开目录只放准备发布的文件，不放截图、压缩备份、隐藏状态或软链接。
5. **检查全文。** 文件内容、文件名、链接目标、注释、代码样例都要看。只有文档需要时才加入图片，并单独检查像素内容、元数据和版权。
6. **运行扫描。** 用本仓库的只读工具查常见标记。报告也要先本地审阅，不把可能包含私人文件名的报告直接贴到公开 Issue。
7. **核对发布载荷。** 人工确认每一个要提交的文件。第一次公开使用全新 Git 历史，不从私人仓库复制 `.git`；确认提交作者邮箱适合公开。
8. **回读远端。** 发布后核对仓库可见性、默认分支、文件清单及实际内容。能打开首页不等于所有文件已经检查过。

## 扫描器能做什么

```sh
python3 -B tools/audit_public.py ./public-export
```

它检查选定目录中的文本文件，查找部分令牌格式、私钥标记、邮箱、用户主目录、网络地址和设备／聊天标识，并拒绝部分非文本类型、隐藏状态与软链接。它不会更改内容，也不会自动“洗白”材料。

它不检查 Git 历史，不做图片 OCR，不识别所有语言中的人名、公司名、客户关系或商业机密，也不能发现所有自定义凭据。报告中没有命中，只能表述为“本次规则未发现命中，仍需人工审阅”。完整边界见 [工具说明](../tools/README.md)。

## 发布前逐项确认

- [ ] 四个专题和示例都经过人工全文阅读。
- [ ] 没有真实个人信息、业务事实、客户原件或私人来源路径。
- [ ] 示例、模板、链接与提交元数据均适合公开。
- [ ] 没有复制受限的第三方内容；许可说明准确。
- [ ] 自动检查通过，所有命中均已解释或修正。
- [ ] 实际 Git 提交与准备发布的文件清单一致；没有私人历史或附件。
- [ ] 产品行为、现场经验和本仓库建议已分开说明。

## 如果已经泄漏

暂停继续传播。若泄漏的是密码、令牌或密钥，优先吊销或轮换，并按提供方流程处理。只删掉当前文件，不能清除已有提交、克隆、分叉和缓存中的副本。历史清理需要单独评估和协调，不在正常整理流程里顺手强推。

参考：[GitHub：从仓库移除敏感数据](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。
