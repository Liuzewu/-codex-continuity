# 07｜运行一次受控的反馈复用演示

这个演示把“候选反馈如何变成现行规则”落实为可检查的文件。它不连接 Codex，不调用模型，也不读取真实知识库。所有项目、反馈、依据和输出均为新编写的虚构样例。

需要 Python 3.9 或更新版本，无第三方依赖。在仓库根目录运行：

```sh
python3 -B tools/demo.py
```

Windows 可使用已安装的 `py -3` 替换 `python3`。程序不接收外部路径，只读取仓库自带的练习包，在自己的临时目录中演示修改；结束后删除临时副本，原始样例保持不变。

## 预期看到什么

程序输出 JSON。正常完成时，`all_assertions_passed` 和 `temporary_files_removed` 为 `true`，`passed` 为 `2`，`expected_failures` 为 `2`，退出码为 `0`。

| 演示步骤 | 操作与结果 | 为什么这样判断 |
| --- | --- | --- |
| `baseline` | 初始练习包和完整输出通过 | “进展／下一步”已是现行规则；“未验证事项”仍是候选。 |
| `unconfirmed_promotion` | 把候选改成 active 并加入路由，检查失败 | 没有补充确认依据，报告 `missing_active_evidence`。 |
| `missing_section` | 补齐虚构确认依据后，检查缺章输出，失败 | 正文虽然提到了尚未检查的工作，但没有独立标题，报告 `missing_required_heading`。 |
| `confirmed_reuse` | 同样的现行规则检查完整输出，通过 | 依据、路由与要求的标题结构一致。 |

两个失败是预期结果。程序同时断言退出码和具体问题代码；若因别的原因失败，或错误样例意外通过，整个演示仍会失败。它不会用“发生了异常”冒充“成功识别了问题”。

## 练习包里有什么

[虚构练习包](../examples/feedback-loop/README.md)包含 `registry.json`、`ROUTING.md`、规则正文、虚构依据与两个输出样例。两个输出的事实内容相同，区别是是否单列“未验证事项”。这让检查聚焦在一个明确要求上。

登记表把两个维度分开：

- `kind` 表示反馈类别：`preference`、`accepted_artifact`、`verified_method`、`project_fact` 或尚未分类的 `observation`。
- `status` 表示生命周期：`candidate`、`active`、`retired`。候选可以保存和修订，但不能作为当前交付要求出现在路由中。

每条规则有独立 ID、适用 `scope`、规则 `family`、唯一正文路径、可选替代关系和标题约束。同一 `scope / family` 不能同时存在两条 active 规则。多个互不冲突的规则可以分别处于不同 family。

active 规则必须关联可读的依据文件，依据类别与反馈类别对应：偏好使用 `user_confirmation`，验收版本使用 `acceptance`，已验证方法使用 `reproducible_result`，项目事实使用 `dated_source`。未分类 observation 不能直接成为 active。检查器检查这些登记条件，不会判断依据是否真实、是否充分或是否仍然有效。

## 只读检查器可以检查什么

`tools/check_knowledge.py <bundle>` 读取指定练习包的登记表、导航及明确引用的文件。可附加 `--check-output RELATIVEFILE`，按所有 active 规则的 `required_headings` 检查一个包内输出。它不遍历主目录，不连接其他设备，不修改登记状态或修复文件。

检查包括唯一 ID、同范围同主题的唯一现行版本、依据引用、active 路由、替代对象是否存在及替代关系有无循环。候选和停用规则不参与输出要求；它们若仍出现在现行路由中，会被报告。

路径采用包内相对路径和 `/` 分隔符；拒绝绝对路径、向上跳转、隐藏路径组件及软链接。引用文件必须是可读的 UTF-8 普通文件，每个文件最多 1 MiB，登记条目最多 200 条。缺失文件、无效编码、不可读文件和特殊文件都不会被当作检查通过。

导航使用简单的内联 Markdown 链接，例如 `[简报](rules/brief-basics.md)`，目标必须是已登记正文；不支持标题参数、锚点、引用式链接或完整 Markdown 语法。标题检查支持 `#` 到 `######` 的 ATX 标题，标题文字须准确匹配；正文中提到同样文字、代码围栏里的标题和 HTML 注释均不算独立章节。检查器只过滤这些常见干扰，不解析 HTML 显示效果、嵌套容器或所有 Markdown 扩展，不能代替打开成品检查。

| 退出码 | 含义 | 后续处理 |
| --- | --- | --- |
| `0` | 本次结构检查通过 | 继续做必要的事实、人工审核与实际交付验收。 |
| `1` | 结构或规则问题 | 根据 JSON 中的问题代码检查元数据、路由或输出；不要自动把候选改成 active。 |
| `2` | 参数、输入或读取错误 | 先解决文件与读取条件，当前结果不能用于宣布通过。 |

## 哪些结论仍然不能得到

`active` 是一项登记声明，不是检查器授予的批准。演示中的确认文件预先随包提供，只在临时流程中模拟关联；这不代表任何真实人员已经审核。

工具也不能证明模型读取了规则、反馈已经保存到产品记忆、另一台设备已收到文件，或成品事实与版式正确。标题齐全甚至可以对应一篇内容很差的简报。因此，离线演示通过之后，真正的复用验收仍应选一项范围明确的任务：实际读取现行正文、生成交付物，再核对事实和用户要求。

不要在被并发修改的目录上把检查结果当成持久保证。检查器不是文件系统隔离边界；一次读取结束后，文件仍可能变化。将本次已验证范围与未验证部分分别记录，沿用[知识复用方法](02-knowledge-reuse.md)和[跨设备五层验收](03-multi-device-sync.md)，无需增加后台模型或生产同步服务。
